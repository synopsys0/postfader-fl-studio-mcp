# Deferred 0.12.0 channel-mix demo plan

Status: **deferred by the release owner; not recorded; non-blocking for
0.12.0**.

No demo exists for this release. The release owner deferred recording until a
dedicated public project is available. This document is retained only as the
future capture plan; do not record against a user project merely to complete
it. When resumed, keep the demo deliberately narrow: play, move one Channel
Rack channel's level and pan, mute it, then stop.

The packaged 0.12.0 candidate completed its separate retained
hardware-in-loop run: 12 of 12 cases passed, all cases were restored, and a
fresh final observation matched the initial fixture. That evidence, not a
video, cleared the hardware gate. A future video will be a public
demonstration only and will not retroactively gate 0.12.0.

The future narrow recording will not replace or broaden that release-wide
evidence. Song position, loop mode, tempo, channel identity, channel routing,
step writes, live-note dispatch/release, the three `channel_generator`
parameter setters, and the new generator inventory/read paths were validated
separately and do not belong in the demo. The published step budget remains:
reads may observe up to 512 cells, verified writes refuse grids over 256, and
each eligible batch must satisfy `step_count + update_count + 8 <= 320`.
Refresh the digest between split calls.

## Privacy-safe fixture and capture

Use a new disposable, unsaved project made only for this recording:

- one stock generator with a generic name such as `Demo Channel`;
- a short manually prepared stock pattern so Play has visible and audible
  activity without using a user's music, samples, presets, or third-party
  plug-ins;
- no imported audio, personal project title, filesystem path, recent-file
  list, account name, notification, serial number, or unrelated desktop window;
- a non-sensitive IAC port name, or crop the port name out of the recording;
- FL Studio launched normally, then write mode enabled from the connected AI
  client with an explicit user-present confirmation. The MCP server receives
  `FL_BRIDGE_ENABLE_MIDI=1` only; no write flag is stored in its configuration.

Close other MCP clients before the run because the production IAC transport is
shared. Capture only the FL Studio window and a sanitized tool-result pane.
Hide the macOS menu bar, project picker, Browser history, and any absolute path.
Do not show the full session fingerprint; a short redacted token is enough to
show that a precondition was supplied.

Before recording, write the following into a private validation note and later
copy only the non-identifying fields into the public evidence record:

- Postfader commit and package version;
- FL Studio edition, exact version and build;
- macOS version and architecture;
- MIDI scripting API version reported by the bridge;
- bridge source digest and transport (`midi`/CoreMIDI IAC);
- Claude Desktop version if the demo is run from the MCPB install;
- capture date in UTC.

Do not fill those fields from memory. Record what the release candidate reports
at capture time.

## Preflight: abort rather than improvise

1. Confirm the disposable project is not recording and contains no user media.
2. Confirm only one live connector owns the selected IAC transport.
3. Call `fl_get_capabilities`. Require a compatible live bridge, production
   MIDI transport, and `verified_writes_enabled: true`.
4. Call `fl_get_project_summary`. Require `recording: false`. Retain the bridge
   session fingerprint for guarded calls, but redact it in public material.
5. Call `fl_list_channels`. Select a non-personal, disposable channel by its
   global index and retain its observation-scoped `channel_fingerprint` plus
   baseline volume `V0`, pan `P0`, and mute state `M0`.
6. Abort if any baseline field is missing, the bridge/version/digest is
   unexpected, the project is not the disposable fixture, or a conflicting
   client is present. Do not switch to a user project to make the demo work.

Choose visibly different but conservative absolute targets without clipping:

- `V1 = 0.65`, unless `V0` is already near `0.65`, then use `0.75`;
- `P1 = -0.25`, unless `P0` is already near `-0.25`, then use `0.25`;
- `M1 = not M0`.

All calls below are absolute setters, not nudges or toggles. Use the final MCP
schema generated by the integrated release candidate; the logical payloads
shown here name the required values and guards.

## On-camera sequence

Keep the Channel Rack and the selected channel controls visible throughout.
Pause after each response long enough to show both the UI change and the proof
fields.

1. **Establish the baseline.** Show the sanitized `fl_list_channels` row for
   the disposable channel: global index, generic name, `V0`, `P0`, and `M0`.

2. **Play.** Call:

   ```text
   fl_set_playing(
     playing=true,
     session_fingerprint=<current session>,
     expected_before={playing: false}
   )
   ```

   Require `requested_playing: true`, `after_playing: true`, `verified: true`,
   later-idle-tick verification, `project_saved: false`, and an explicit undo
   observation. Starting playback must not be presented as an undoable edit.

3. **Move the channel fader.** Call `fl_set_channel_mix` with the selected
   `channel_index`, absolute `volume_normalized=V1`, the current session
   fingerprint, and `expected_before` containing the channel fingerprint and
   `volume_normalized=V0`. Require `volume_verified: true`, `verified: true`, a
   later-tick `after.volume_normalized` matching `V1`, an explicit undo
   observation, and `project_saved: false`. Unrequested pan/mute proof fields
   must remain null.

4. **Move channel pan.** Call `fl_set_channel_mix` with absolute `pan=P1` and an
   `expected_before` guard containing the channel fingerprint and `pan=P0`.
   Require `pan_verified: true`, aggregate `verified: true`, a matching
   later-tick readback, the undo observation, and `project_saved: false`.

5. **Mute the channel.** Call `fl_set_channel_mix` with explicit `muted=M1` and
   an `expected_before` guard containing the channel fingerprint and
   `muted=M0`. Require `mute_verified: true`, aggregate `verified: true`, a
   matching later-tick readback, the undo observation, and
   `project_saved: false`. Describe this as setting mute state, never as
   toggling mute.

6. **Stop and rewind.** Call:

   ```text
   fl_stop(
     session_fingerprint=<current session>,
     expected_before={playing: true}
   )
   ```

   Require `after_playing: false`, `after_song_position_normalized: 0.0`,
   `playing_verified: true`, `position_verified: true`, and aggregate
   `verified: true`. Show `project_saved: false` and the explicit undo
   observation.

7. **Confirm the final observation.** Call `fl_get_transport_state` and
   `fl_list_channels`. Show stopped transport and the requested channel mix
   values. This independent read is additional evidence; it does not replace
   each mutation's own later-tick proof.

If any mutation times out or returns an ambiguous outcome, do **not** replay it
automatically. Make a fresh read, report what is observed, stop the demo, and
retain the failure record. If transport may still be playing, stop it manually
in FL Studio only after capturing the ambiguity.

## Explicitly out of scope

Do not call or demonstrate any of the following in this recording:

- `fl_route_channel_to_mixer` or either mixer-send tool;
- `fl_get_step_sequence` or `fl_set_step_sequence`;
- plug-in parameter writes or plug-in insertion;
- note audition, tempo, loop-mode, song-position, render, save, autosave, undo,
  or arbitrary API behavior.

Plug-in insertion is **Unavailable through public MIDI scripting backend.** Do
not call it impossible, and do not substitute UI automation for a public MCP
tool.

## Cleanup and retained evidence

After the on-camera stop, restore `V0`, `P0`, and `M0` with guarded absolute
`fl_set_channel_mix` calls and verify each later-tick result. Then close the
disposable project without saving. Restoration is cleanup, not part of the
public demo claim; if restoration cannot be verified, preserve the failure and
close without saving rather than guessing.

If the owner resumes this plan, retain these draft deliverables without
publishing them until review:

- `postfader-0.12.0-channel-mix-demo.mp4` — cropped public video;
- `postfader-0.12.0-channel-mix-demo.md` — accessible transcript/captions;
- `postfader-0.12.0-channel-mix-hil.json` — allowlisted evidence fields only;
- a SHA-256 digest for each deliverable.

The evidence JSON should contain the environment fields, tool names, sanitized
inputs, requested/before/after values, per-field proof flags, aggregate
`verified`, verification basis, undo observation, `project_saved`, and outcome.
It must omit project names and paths, usernames, raw session fingerprints,
MIDI endpoint identifiers, audio, plug-in inventories, and unrelated tool
output.

The future demo passes only when all five live mutations (play, volume, pan,
mute, stop) produce the expected later-tick proof, no automatic replay occurs,
no project save occurs, and no routing or sequencer command appears in the
trace. Deferring that recording does not lower the evidence labels in the
capability matrix and does not block the 0.12.0 release.
